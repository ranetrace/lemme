# Changelog

All notable changes to `ranetrace/lemme` will be documented in this file.

## Unreleased

### Added
- Every documentation page now has a Markdown twin at its own URL: append `.md` to any page URL (`/docs/getting-started.md`) to get the raw Markdown source, with the same `Content-Type: text/markdown` and `X-Markdown-Tokens` headers the `Accept: text/markdown` mode already returned. Agents and tools that cannot set request headers can now fetch documentation directly. The docs home page is served at `/docs/index.md`, since its own slug is empty. HTML pages advertise their twin with a `<link rel="alternate" type="text/markdown">` tag in the `<head>`. The twin routes follow the existing `lemme.markdown.enabled` flag, so setting `LEMME_MARKDOWN_ENABLED=false` leaves both the routes and the link tag out.
- New `lemme.markdown.renderer` config key naming the class Lemme builds per render, so an application that highlights code its own way can render its documentation the same way. It defaults to Lemme's own `Ranetrace\Lemme\Support\MarkdownRenderer` (see the fix below) and accepts any class extending `Spatie\LaravelMarkdown\MarkdownRenderer` that keeps that constructor's signature, since the theme, extensions and CommonMark options are passed as named arguments. A class that does not extend it throws an `InvalidArgumentException` naming the configured class, rather than failing later inside a page render. Documented under "Customizing Markdown Rendering" in the README.

### Fixed
- Search result excerpts are plain text again, instead of the tag fragments and class names that used to surface mid-sentence (`... RANETRACE_ERRORS...cent">ant">erline bg-transparent text-...`). Fuse reports its match indices against the value it indexed, which is a page's whole content, and the view handed the highlighter a copy of that content truncated to 120 characters. Every index past the end of the truncated string appended a highlight element to it, and the next index then landed inside that element and spliced a second one into the middle of its `class` attribute, which the browser parses as content. The excerpt is now cut in the browser, in the coordinates the indices are expressed in, and the window opens just before the first match rather than always at the start of the page, so the word that was searched for is in the piece the reader sees. Highlighting escapes the text it marks, piece by piece around the highlight elements, so a title or an excerpt that is itself markup renders as text rather than as markup; the fallback strings the view renders before the browser has match data are escaped server side for the same reason. The index itself is plain text more thoroughly too: entities the renderer escaped (`&lt;`, `&amp;`) are decoded back to the characters the page shows, so a query for them matches and an excerpt does not escape them twice, and `lemme.search.max_content_length` now counts characters rather than bytes, since half a multi-byte character is not valid UTF-8 and the whole index is `json_encode`d on its way to the browser.
- Documentation search works on a site with `lemme.cache.enabled` set to `false`. The pages arrive keyed by slug, and the uncached path handed the search index straight through with those keys, so it serialised to a JSON object instead of an array. `new Fuse(object)` has no collection to iterate and every query returned nothing, silently. The index is re-indexed as a list before it leaves the builder, which is what the cached path was already doing by passing `values()` in. Sites with caching on were never affected.
- The `@source` paths in `src/input.css` point at the files they name. Both were written relative to the project root while Tailwind resolves them relative to the stylesheet, so `./resources/views/**/*.blade.php` and `./src/**/*.php` resolved inside `src/` to directories that do not exist, and only Tailwind's automatic detection was finding the Blade views. No change to the shipped stylesheet.
- The docs layout now has the landmarks a screen reader and a keyboard navigate by. The page content sits in a `<main id="main-content">`, which is new: there was no main landmark at all, so "skip to the content" had nothing to skip to. A skip link to it is the first focusable element in the `<body>`, hidden until it takes focus, which spares a keyboard visitor the navigation toggle, the logo, the search and the theme switcher on every page. Each of the three `<nav>` elements now carries a name: the sidebar and the mobile panel are labelled "Documentation", since they are one navigation the layout renders at two widths and only one of them is exposed at a time, and the table of contents is labelled "On this page". Unlabelled they were announced as three identical navigation regions.
- The docs search field is now named and shows where the focus is. It had no label, no `aria-label` and no `id`, so it was announced as an unnamed edit field; it now carries `id="lemme-search"` and a visually hidden label reading "Search the documentation". Its `outline-hidden` suppressed the focus outline with nothing in its place, leaving a keyboard visitor no way to see where they were, and is replaced by a `focus-visible` outline in the accent colour, drawn inside the box because the panel clips whatever crosses its rounded edge. The results list is now named "Search results", and its `role="listbox"` is dropped: a listbox promises arrow key navigation and an active option reported through `aria-activedescendant`, and the results are plain links reached with Tab, so the role took the links out of the reading a screen reader gives them and handed nothing back. Wiring the full combobox pattern is the fix for that, and lands in the entry below.
- The docs search is a real combobox, so the results can be walked from the keyboard. `role="combobox"` used to sit on a `<div>` wrapping the form, with an `aria-expanded` hardcoded to `false` and no `aria-controls` at all, which described a widget that did not exist. The role is now on the field itself, alongside `aria-autocomplete="list"`, `aria-haspopup="listbox"`, an `aria-expanded` that follows whether results are showing, and an `aria-controls` naming the results list. The list is a `listbox` again, each result an `option` with its own id, and the field points at the active one through `aria-activedescendant` while the caret never leaves the field. Arrow down and arrow up move the active option and wrap at both ends, Home and End jump to the first and last result, Enter follows the active result, and Escape still closes the modal. The active option scrolls itself into view. Enter with no active result no longer submits the surrounding form, which reloaded the page out from under the modal. The results are out of the tab order now, as a combobox's options should be: Tab leaves the widget rather than walking the list. Hovering a result makes it the active option rather than lighting a second row, and the highlight itself hangs off `aria-selected`, so the pointer and the keyboard can never disagree about which result is current. The list is rendered empty and hidden rather than left out while there is nothing to show, because `aria-controls` has to resolve to an element that is on the page.
- Fenced and indented code blocks now keep their `<pre>` element on every path, so a multi-line snippet stays a block instead of collapsing onto one line as inline text. Spatie's renderer hands the `<code>` element to Shiki and returns the result in place of the whole `<pre>`, which is correct only while Shiki answers, because a highlighted block brings its own `<pre class="shiki">` wrapper. Shiki throws on a language it does not know, such as ` ```env `, and it throws on every block at once when the web server cannot reach a Node binary, which is the usual case under PHP-FPM, where the PATH does not carry a version manager's directory; in both cases what reached the page was a bare `<code>`, which browsers render inline and the prose stylesheet decorates with literal backticks. Lemme now renders code blocks through its own `MarkdownRenderer`, which registers a code block renderer above Spatie's and returns the whole element, stepping aside only for highlighted markup that already is a block. This replaces the pattern match over the finished HTML added earlier in this cycle, which could only recognise blocks that carried a `language-*` class and so left a fence with no language, and every indented block, still inline. Rendered pages are cached by their own modified time, so a site with `lemme.cache.enabled` on keeps serving the old markup for pages nobody has edited: run `php artisan lemme:clear` after upgrading.
- `composer analyse` runs again. There was no `phpstan.neon` in the repository, so PHPStan stopped at "At least one path must be specified" before analysing anything. The config analyses `src` and `routes` at level 5 and passes clean. It leaves `config` out: Larastan's rule against `env()` outside the config directory resolves that directory from the booted application, which for a package is the host application's and never the package's own, so every `env()` call in `config/lemme.php` was reported as an error.
- The search index is built through the same renderer a documentation page is rendered through. `SearchIndexBuilder` resolved spatie's container binding and configured that, so the index was built with the host application's `config/markdown.php`, while the page went through the class named by `lemme.markdown.renderer` carrying Lemme's extensions and CommonMark options. Two renderers over one document means a phrase can be on the page and missing from the index, or matched in the index and absent from the page the reader is then sent to. Both now build through one `MarkdownRendererFactory`, so `lemme.markdown.renderer` is honoured for the index too, and a configured class that does not extend spatie's renderer is rejected by name there as well. The index still renders with highlighting off, since it only needs plain text and Shiki is the part of the pipeline that shells out to Node. Documentation using tables, task lists, strikethrough or any other configured extension is now indexed as the text the page shows rather than as raw Markdown, which is a better index and a different one: run `php artisan lemme:clear` after upgrading to rebuild it on a site with the cache on.

### Security
- The docs search no longer renders whatever is posted to its `search-results` Livewire listener. The listener is reachable from a browser console with any payload, and the view prints what it is handed: the `url` goes straight into an `href`, where Blade's escaping does nothing about a `javascript:` scheme, and the title, category and excerpt are read back out as text. Every entry now has to fit the shape the index sends before it reaches the view, which means a `title`, `category`, `content` and `slug` that are strings, an optional `score` that is a JSON number between 0 and 1, and a `url` that points at this site: a root-relative path (rejecting `//host` and `/\host`, which a browser reads as protocol-relative), or an absolute `http`/`https` url on the application's host or on the configured documentation subdomain. Page urls are built with `url()`, so an absolute url is the form the index actually carries. Whitespace and control characters are rejected anywhere in a url, since they are what splits a scheme into something a url parser reads as a path while a browser still runs it. One entry that does not fit rejects the whole payload rather than being dropped from it, because the browser sends the index back as it received it, so a single misshapen entry means the payload is not ours, and a list that is quietly one entry shorter still looks like a search result. Entries are rebuilt from the keys the view reads, so nothing else rides along into the component's state: Fuse's `matches` used to make that round trip on every keystroke, and the browser reads those from the search instance it already holds. The payload is capped at five entries, the number the view asks the search instance for, and the view now renders that number from the same constant so the cap and the request cannot drift apart. Nothing to change in an application that uses the shipped component; an application dispatching `search-results` itself has to send the keys above.

## v3.0.6 - 2026-05-19

### Fixed
- The "On this page" table of contents no longer shows phantom entries for `#`-prefixed lines (e.g. shell comments) inside fenced or indented code blocks. Headings are now collected from the CommonMark AST using the same parser that renders the page, so code-block content can never leak into the TOC and anchor `id`s stay aligned with the rendered headings by construction.

## v3.0.5 - 2026-05-18

### Added
- Configurable favicon for the docs layout via a new `lemme.favicon` config block (`LEMME_FAVICON_*` env vars), mirroring the existing `logo` pattern. Supports `type=file` (`<link rel="icon">` plus optional apple-touch-icon) and `type=view` (render your own Blade partial in `<head>` for a full modern set). Opt-in: the default `type=none` emits nothing, leaving the docs `<head>` byte-identical to before — no change for existing installs on upgrade. See the "Favicon Customization" section in the README.

### Fixed
- Docs search no longer fails to initialize when Livewire boots before the deferred search bundle. The search instance is now created synchronously and the Livewire data request is order-independent, so `lemmeSearchInstance not available` no longer occurs on a fresh full page load.

## v3.0.4 - 2026-05-18

### Added
- Markdown tables (and the rest of GitHub Flavored Markdown) render out of the box. The `GithubFlavoredMarkdownExtension` is enabled by default.
- New `lemme.markdown.extensions`, `lemme.markdown.highlight_theme`, and `lemme.markdown.commonmark_options` config keys for customizing CommonMark extensions, the Shiki theme(s), and CommonMark options without forking. See the "Customizing Markdown Rendering" section in the README.

### Changed
- Lemme now uses a dedicated `Spatie\LaravelMarkdown\MarkdownRenderer` instance per render instead of mutating the container-bound one. Rendering documentation no longer leaks Lemme's extensions or options into the host application's `MarkdownRenderer` (e.g. for blog posts, comments, glossary content).
